# Contributing to Vanta

## Useful contributions

Start with AGENTS.md, DELIVERY-POLICY.md and BACKLOG.md. Use the current day's existing scope; preserve the product identity, private data boundaries and manual schedule. A useful first contribution is a minimal synthetic JSON parsing/diagnostic case with expected line and column. Include minimal synthetic input, exact steps, expected/actual behavior and relevant environment details. Avoid posting private payloads, customer information or machine configuration.

A product explanation worth developing during the existing documentation tickets is a local-processing walkthrough and malformed-input examples. Keep setup instructions executable, screenshots accurate and limitations explicit. Do not claim unimplemented persistence, live integrations or accessibility guarantees.

## Issues, PRs and collaboration

- Open an issue only for a real unresolved problem or concrete improvement. Search for duplicates; link existing reports. Close it from the verified fix only when its criteria are met. Do not create/close placeholders for activity counts.
- Keep a repository-specific branch and PR targeting main. Explain this product's behavior, evidence and limitations. Follow every panel-review/check/merge gate in DELIVERY-POLICY.md; a badge or time target cannot replace review. Choose commit boundaries from actual work with no quota.
- Credit a genuine collaborator's actual contribution. Before adding Co-authored-by, confirm their chosen name and GitHub-associated email (prefer their no-reply address for privacy). No invented identities or automatic human credit for agent runs. Follow [GitHub's coauthor instructions](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors).
- If relevant Q&A Discussions already exist, prepare reproducible answers to real questions; an authorized human decides acceptance. External posting or contacting people requires explicit user authorization. Do not enable Discussions or change permissions/settings as a side effect.

## Profile recognition follows useful work

Reference: [community achievement catalogue](https://github.com/Schweinepriester/github-profile-achievements), checked 2026-10-27; unofficial and subject to change. Account-wide achievements are secondary outcomes, never per-project activity quotas or promises.

- Pull Shark can follow merged substantive PRs. Pair Extraordinaire needs genuine coauthored merged work. Galaxy Brain depends on actual accepted eligible Discussion answers; GitHub Community Discussions are excluded according to the catalogue.
- Starstruck depends on voluntary audience interest. Improve useful examples and documentation; no traded, purchased or alternate-account stars. No outreach is authorized by this guide.
- Quickdraw may occur naturally when a real issue/PR is resolved quickly; do not rush checks or create throwaway issues. YOLO may be observed under existing permitted gates, but author panel inspection and required independent approvals remain mandatory. Never remove reviews/protections to pursue it.
- Finishing Touch concerns GitHub's own UI, not this product's UI. Public Sponsor requires a separate personal payment decision. Historical Arctic/Mars badges and internal Proxima recognition are not new project deliverables; disabled/testing Heart On Your Sleeve and Open Sourcerer have no active target.

## Fit the existing 30-day plan

At daily startup, consider whether today's actual change offers a useful report, example, explanation or genuine collaboration; record none if none exists. During already planned weekly reviews, triage real feedback and assess one relevant contribution opportunity if available. During existing setup/documentation tickets, refine the product example above; Day 30 summarizes actual evidence. Do not shift completed days or introduce feature work solely for an achievement.

In DAILY-LOG.md, record real issue/PR URLs, collaboration scope and observed answer/profile evidence when available. Distinguish observed, eligible but unconfirmed, externally dependent and unavailable; a count alone proves no badge. Final PR merge facts go in the portfolio delivery receipt and are reconciled at the next authorized log update.
